# RAG evaluation utilities

[All utility groups](../README.md)

These tools evaluate retrieval and generated answers against saved robot-manual
evidence. They cover object retrieval, category-only questions, task retrieval,
question authoring, and supplemental sample banks. They open existing indexes;
index construction belongs to the [embedding workflow](../embedding/README.md).

All shell commands below run from the repository root. Use the project's
`.venv/bin/python`; CLI scripts also support `python -m utils.rag.<module>`.

## Modules

| Module | Role | Interface |
| --- | --- | --- |
| [object_rag_evaluation.py](object_rag_evaluation.py) | Source sampling, query embedding cache, frozen-evidence replay, persistent runs, and metrics | `EvaluationRun`, `QueryEmbeddingCache`, `grouped_metrics` |
| [object_rag_category_questions.py](object_rag_category_questions.py) | Category-only question wording, category prompts, and answer/source-location displays | `CategoryPromptGenerator`, `CategoryEvaluationRun` |
| [run_object_rag_evaluation.py](run_object_rag_evaluation.py) | Author notebook cases, prepare query embeddings, run evaluations, and publish results | CLI stages: `author-offline`, `build`, `prepare`, `run`, `publish` |
| [review_object_rag_evaluation.py](review_object_rag_evaluation.py) | Separately judge completed answers against source references | CLI; optional `--watch` and `--all-cases` |
| [task_rag.py](task_rag.py) | Task-only retrieval, answer contract, coverage checks, reranking, and task metrics | `TaskRAG`, `TaskEvaluationRun`, `task_index_coverage`, `require_task_coverage` |
| [task_rag_questions.py](task_rag_questions.py) | Select workbook sources, enumerate complete tasks, author one question per task, and validate atomic banks | `TaskQuestionAuthor`, `load_task_bank`, `select_cases` |
| [rag_evaluation_samples.py](rag_evaluation_samples.py) | Load and audit supplemental sample banks without a model | CLI; `load_sample_bank`, `audit_summary` |
| [generate_regular_object_samples.py](generate_regular_object_samples.py) | Deterministically extract regular-object questions from local manuals | CLI; default count: 3,000 |
| [generate_program_rag_samples.py](generate_program_rag_samples.py) | Generate several grounded questions per saved task | CLI; default count: 1,000 |

## Prerequisites and configuration

Prepare the generated runtime modules before importing the evaluation helpers:

```sh
uv sync --locked
uv run ribosome-prepare --profile standalone
```

Preparation exports Python modules without executing notebook workflows or
calling models. See [preparation profiles](../../docs/preparation-profiles.md)
for backend integration and alternate output directories.

For live evaluation, the selected index must already contain `catalog.sqlite3`
and `chroma/`, with vectors generated by the matching embedding model/provider
configuration. The object notebook opens collection `object_summaries`; the task
notebook opens `task_embeddings`. Category mappings live in
`proj_config/coding_categories/`. CSV-based case regeneration also requires
`assets/code-docs/product_manuals_markdown.csv` and its referenced Markdown files.

The notebooks load the project `.env` with existing environment values taking
precedence. Their main settings are:

| Setting | Use / default |
| --- | --- |
| `OLLAMA_EMBED_MODEL` | Embedding model; `qwen3-embedding:8b` |
| `OLLAMA_RAG_MODEL` | Generation and question-authoring model; falls back to `OLLAMA_SUMMARY_MODEL` |
| `OLLAMA_API_KEY` | Optional bearer authentication for model clients |
| `OBJECT_RAG_INDEX` | Object index override; otherwise `db/object_embeddings/<model>-<embedding-host>` |
| `TASK_RAG_INDEX` | Task index override; otherwise `db/task_embeddings/<model>-<embedding-host>` |
| `OBJECT_RAG_CATEGORY_BOOST` | Object category score boost; `0.15` |
| `TASK_RAG_CATEGORY_BOOST` | Task category score boost; `0.15` |

Model directory names replace `/` with `_` and `:` with `-`; host directory
names replace `:` with `-`. The application endpoints come from
[ribosome/ollama_config.py](../../ribosome/ollama_config.py): embedding uses
`http://172.27.74.49:11434`, generation uses `http://172.27.74.16:11434`, and
clients bypass environment HTTP proxies. Setting `OLLAMA_HOST` does not override
those endpoints. The notebook defaults include top-k 8, evaluation concurrency 2,
24,000 context characters, 2,048 output tokens, and a 300-second request timeout.

## Tutorial: run and review the object evaluation

The CLI uses the banks and setup cells in
[06.test.rag.object.question_with_location.ipynb](../../nbs/06.test.rag.object.question_with_location.ipynb).
The committed banks are sufficient for an existing-index evaluation; no case
regeneration is required. The full notebook bank has 828 cases: 68 historical
cases plus 760 sampled cases from 38 CSV manual entries.

1. Prepare the query embedding cache. This contacts the embedding service and
   writes query cache/results metadata, without generating answers:

   ```sh
   .venv/bin/python utils/rag/run_object_rag_evaluation.py prepare
   ```

2. Run retrieval and answer generation:

   ```sh
   .venv/bin/python utils/rag/run_object_rag_evaluation.py run --concurrency 2
   ```

   `run` normally prepares missing query embeddings first. If another process is
   preparing that cache, `run --skip-prepare` consumes saved vectors and embeds
   individual misses on demand. Rerun the same command after an interruption to
   reuse compatible completed retrieval and answer stages.

3. In a second terminal, review arriving answers using the generation host:

   ```sh
   .venv/bin/python utils/rag/review_object_rag_evaluation.py \
     --host http://172.27.74.16:11434 --concurrency 2 --watch
   ```

   The reviewer makes separate model calls. Its default selection covers all 68
   historical cases and three different tasks per CSV source, totaling 182
   cases. Use `--all-cases` to review every case. Without `--watch`, it processes
   currently available terminal results and exits. Reviewer defaults are context
   32,768 and timeout 120 seconds; `--context` and `--timeout` override them. Its
   CLI host default is the embedding host, so the example sets the generation
   host explicitly.

4. Publish saved results into the notebook and Markdown review:

   ```sh
   .venv/bin/python utils/rag/run_object_rag_evaluation.py publish
   ```

   `publish` makes no model calls. It reads the saved run identified by
   `latest.json` only when its identity matches the current configuration,
   refreshes notebook result displays, and writes the review report. Without
   compatible saved results it preserves existing result displays rather than
   replacing them. A completed generation is not a correctness judgment;
   unreviewed cases remain unreviewed.

### Artifacts and reuse

| Path | Contents |
| --- | --- |
| `db/object_rag_tests/query_embeddings/` | Query vectors isolated by model, provider settings, and dimension |
| `db/object_rag_tests/results/<run-id>/` | Run manifest, immutable case-bank snapshots, per-case retrieval/answer JSON, and `metrics.csv` |
| `db/object_rag_tests/latest.json` | Current run and case-bank pointers |
| `db/object_rag_tests/results/<run-id>/reviews/<review-id>/` | Judge results, raw model responses, and validation warnings |
| `db/object_rag_tests/results/<run-id>/review-plan.json` | The qualitative review selection |
| `db/object_rag_tests/review.md`, `published-metrics.csv` | Published Markdown report and metrics snapshot |

Run identities include active index generations, mapping/catalog settings,
embedding and generation configuration, top-k, limits, and relevant answer
implementation sources. Changed settings receive a separate run namespace;
previous results remain available. Case files are published atomically. Failed
retrieval or generation stages can be retried while completed stages are reused.
The snapshot cache stops if the active index changes during a run. These caches
do not rebuild the corpus, index, or summarization checkpoints.

### Optional: regenerate the notebook's sampled cases

Only use this workflow when intentionally changing the notebook case bank:

```sh
.venv/bin/python utils/rag/run_object_rag_evaluation.py author-offline
.venv/bin/python utils/rag/run_object_rag_evaluation.py build
```

`author-offline` reads the CSV/manual sources and saves content-addressed
authoring records under `db/object_rag_tests/authored/`, without model calls.
`build` uses those records to replace the notebook section beginning at “CSV
manual sampling tests.” It recreates the appended cases and result cells; run
`publish` afterward to restore compatible recorded result displays.

## Tutorial: audit and generate supplemental banks

Supplemental banks have a different contract from the exhaustive task bank.
The regular bank contains 3,000 object questions; the program bank contains
1,000 questions over 126 source tasks. Multiple program questions may refer to
one task and are not independent programs. Use `load_sample_bank` for these
files, rather than `load_task_bank`.

Inspect the committed banks locally, without services:

```sh
.venv/bin/python utils/rag/rag_evaluation_samples.py \
  evaluation_samples/regular_object_rag_3000.json \
  evaluation_samples/program_rag_1000.json
```

Add `--source-root .` when this checkout contains the referenced `assets/` and
task JSON files. That also checks file hashes, exact Markdown line excerpts,
and saved task IDs/content. In a vendored checkout, pass the workspace directory
that owns those source paths instead.

For a separate experimental bank, write to a new output path:

```sh
.venv/bin/python utils/rag/generate_regular_object_samples.py \
  --source-root . --count 3000 \
  --output db/rag_samples/regular_object_rag_3000.json
.venv/bin/python utils/rag/generate_program_rag_samples.py \
  --source-root . --count 1000 \
  --output db/rag_samples/program_rag_1000.json
```

Both generators read local sources and make no model calls. The regular
generator requires profile 4.0/5.0 `*_semantics.json` objects and their paired
Markdown manuals under `assets/code-docs.4.0/` and `assets/code-docs.5.0/`. The program generator
requires `db/task_rag_tests/question_with_tasks/bank.json` and its unchanged
source task files. Their default output paths are the committed files under
`evaluation_samples/`; `--output` in the example keeps those banks intact.
Generation fails if the requested count cannot be grounded in distinct eligible
questions. Keep related task/content questions together when splitting datasets.

Load a bank from Python:

```python
from utils.rag.rag_evaluation_samples import audit_summary, load_sample_bank

bank = load_sample_bank("evaluation_samples/regular_object_rag_3000.json")
print(audit_summary(bank))
print(bank["cases"][0]["question"])
```

The [sample-bank guide](../../evaluation_samples/README.md) shows how to pass a
regular bank to `CategoryEvaluationRun` or a program bank to `TaskEvaluationRun`
in the existing notebooks.

## Tutorial: task authoring and task-only retrieval

1. Open
   [06.test.rag.object.question_with_tasks.ipynb](../../nbs/06.test.rag.object.question_with_tasks.ipynb).
   Inspect the workbook selection and enumerated task counts before running
   question authoring. The workbook is
   `proj_config/coding_categories/coding_manuals_markdown.all.xlsx`; inputs are
   complete `*_tasks.json` files in the selected corpus profiles.
2. Run its authoring cells. `TaskQuestionAuthor.publish(...)` makes model calls,
   validates one question per selected task, and retains content-addressed retry
   records. It publishes `db/task_rag_tests/question_with_tasks/bank.json` only
   after every question succeeds. Rerun the cell to retry failures while keeping
   the previous published bank.
3. Open [05.application.rag.task.ipynb](../../nbs/05.application.rag.task.ipynb).
   Set `SELECTED_CASE_IDS` to known case IDs for a smaller run, or leave it as
   `None` for all cases. Keep `task_index_coverage` and `require_task_coverage` in
   the index-opening cell: they detect missing documents/tasks/vectors and stale
   task content before retrieval.
4. Run the query-cache, retrieval, answer, and cleanup cells in order. The
   notebook uses `TaskRAG`, `TaskEvaluationRun`, and category reranking, with
   results and query caches beside the task bank. `TaskRAG` accepts only task
   records and retains each task's complete evidence. Its answer schema includes
   procedure and parameter fields; code is optional when the evidence supplies
   no code example.

The task helpers are libraries, not standalone CLIs. These notebooks supply
their clients, index, mappings, selection manifest, and cleanup lifecycle.

## Evidence boundaries and troubleshooting

Only the question and category are query inputs. Expected facts, source paths,
revisions, excerpts, and task IDs are reviewer metadata; never concatenate them
into generation prompts. `EvidenceReplay` generates from frozen retrieved
evidence, so an answer retry does not silently retrieve different context.
Category display helpers may reveal source locations in the result view without
turning them into generation hints. Model-assisted judgments are saved separately
from retrieval diagnostics and retain their raw judge output.

| Symptom | Action |
| --- | --- |
| Missing generated `ribosome` module | Prepare the runtime exports using the setup command above. |
| Missing `catalog.sqlite3` / collection or task coverage failure | Select the matching existing index; use the embedding notebook to complete genuinely missing/stale indexed work before evaluating. |
| No generation model or unreachable service | Check `.env`, the configured model, fixed endpoint constants, and optional API key. The reviewer has its own `--host`. |
| Source/workbook hash mismatch | Inspect the changed source and intentionally regenerate the corresponding question bank; retain the previous bank and results for comparison. |
| Active index changed / saved identity mismatch | Stop the changing index writer, then rerun with its actual configuration. Keep prior result directories; do not edit manifests to force compatibility. |
| Some cases have no review | Check the default qualitative selection or use `--all-cases`; completed generation alone does not imply a reviewed answer. |
